Winter ’27 ships platform API version 68.0. But the most important detail for an LWC upgrade is less dramatic: **Salesforce documents no version-specific LWC changes in API 68.0.** That makes this a useful maintenance opportunity—not permission to replace every version number without testing. See [Get the Latest LWC Changes with LWC API Version 68.0](https://help.salesforce.com/s/articleView?id=release-notes.rn_lwc_versioning.htm&language=en_US&type=5) and [The Salesforce Developer’s Guide to the Winter ’27 Release](https://developer.salesforce.com/blogs/2026/10/developers-guide-to-the-winter-27-release).

My recommended approach is simple: separate the Salesforce release upgrade from the component version upgrade, compare behavior in a controlled environment, and promote only what you can explain.

This playbook covers that process, including a deployable LWC example and the evidence I would require before approving production deployment.

- **Instance verification:** Administrators should check their specific instance against the maintenance calendar.

Keep feature status separate from release status. ## What component API versioning actually controls

An LWC bundle’s `apiVersion` selects the **version-dependent LWC framework behavior for that custom component**. Its HTML, CSS, and JavaScript share that version. A parent and child can use different versions; the parent does not automatically upgrade the child. Salesforce documents these boundaries in [Version Lightning Web Components](https://developer.salesforce.com/docs/platform/lwc/guide/create-version-components.html).

At the implementation level, versioning can affect how the framework parses, compiles, and executes a component. A documented historical example is the change to obfuscated CSS scope tokens in API 59.0. These are specific framework behavior gates—not a frozen copy of the entire Salesforce runtime. See [Introducing Component-Level API Versioning for LWC](https://developer.salesforce.com/blogs/2024/01/introducing-component-level-api-versioning-for-lwc).

Use this boundary table during review:

| Concern | Controlled by the custom component’s `apiVersion`? | Upgrade implication |
|---|---|---|
| Version-gated LWC framework behavior | Yes | Review changes between the starting and target versions |
| HTML, CSS, and JavaScript within that bundle | One shared version | Treat the bundle as the upgrade unit |
| Nested custom component | Uses its own version | Test the interaction without assuming version inheritance |
| Lightning base components | No; they use the latest implementation | Retaining an older custom-component version does not freeze them |
| Lightning Data Service | No; it uses the latest implementation | Retaining an older version does not freeze data-service behavior |
| Lightning Locker version | Set at org level | Do not treat a metadata version change as a security-runtime switch |

These distinctions are documented in [Version Lightning Web Components](https://developer.salesforce.com/docs/platform/lwc/guide/create-version-components.html) and [XML Configuration File Elements](https://developer.salesforce.com/docs/platform/lwc/guide/reference-configuration-tags.html).

There is also an important legacy case: previously saved unversioned components can continue running, but saving modifications requires an explicit API version. Salesforce adds the existing effective version when retrieving an unversioned component. Preserve that baseline rather than assuming that adding a version must also mean upgrading it. See [Version Lightning Web Components](https://developer.salesforce.com/docs/platform/lwc/guide/create-version-components.html).

## What “no version-specific changes” means for your upgrade

For a component already on 67.0, moving to 68.0 crosses no newly documented LWC behavior gate specific to 68.0. For a component on an older version, the journey can still cross changes introduced in intervening releases. The [API 68.0 release note](https://help.salesforce.com/s/articleView?id=release-notes.rn_lwc_versioning.htm&language=en_US&type=5) explicitly recommends advancing one version at a time.

Do not conflate these two changes:

1. Running existing component metadata on an upgraded org.
2. Changing that component’s metadata to select a later framework version.

My recommended comparison is:

| Test stage | Org environment | Component version | Question |
|---|---|---|---|
| Historical baseline, if captured | Previous release | Existing version | What worked before the platform upgrade? |
| Current-release baseline | Winter ’27 sandbox | Existing version | Does the unchanged component work on the upgraded platform? |
| Candidate | Same Winter ’27 sandbox | 68.0 | Does changing the component version introduce a difference? |

If you did not capture a pre-upgrade baseline, say so. Do not reconstruct one from memory and present it as measured evidence.

Keep the current-release baseline and candidate comparable: same users, records, page configuration, browser, and security settings. Otherwise, you are testing several variables at once.

## Choose an upgrade strategy deliberately

The following is a **hypothetical architecture scenario**, not a customer engagement: a team owns record-page widgets, shared form controls, and a service-console workspace.

I would use this decision matrix:

| Situation | Recommended action | Evidence required |
|---|---|---|
| Isolated component on 67.0 with strong tests | Upgrade in the first batch | Current-release baseline and candidate pass |
| Shared child used across many pages | Upgrade after consumer inventory | Representative parent-child workflows pass |
| Component several versions behind | Advance incrementally in sandbox | Warnings resolved and behavior checked at each step |
| Third-party library or manual DOM manipulation | Isolate in a dedicated batch | Browser-level interaction and security testing |
| Business-critical component without meaningful tests | Retain current version temporarily | Named owner, test backlog, and review date |
| Target org does not support 68.0 | Stop deployment | Confirm target release support first |

Salesforce validates component API versions against the supported range, with the current Salesforce release determining the latest valid version. See [Version Lightning Web Components](https://developer.salesforce.com/docs/platform/lwc/guide/create-version-components.html).

### Small, medium, and enterprise scale

For a **small estate**, start with a component inventory and a short checklist covering every business-critical screen. Avoid building a complicated rollout system before you have useful tests.

For a **medium estate**, group components by dependency and business workflow. Assign an owner to each batch, retain test evidence, and promote independently where practical.

For an **enterprise estate**, add package boundaries, namespace dependencies, multiple orgs, accessibility requirements, and vendor ownership to the inventory. Require explicit evidence for shared components rather than assuming a successful leaf-component test proves the whole application.

These are recommended governance levels, not Salesforce component-count thresholds. Let dependency reach and business impact determine the process.

## Build a comparison component that exercises real dependencies

Here is a complete, read-only Account component for a Winter ’27 sandbox. It deliberately avoids adopting new template syntax during the version upgrade.

Create the following files under `force-app/main/default/lwc/accountVersionProbe/`.

### JavaScript: explicit data and failure states

```javascript
// accountVersionProbe.js
import { LightningElement, api, wire } from 'lwc';
import { getRecord, getFieldValue } from 'lightning/uiRecordApi';
import NAME_FIELD from '@salesforce/schema/Account.Name';
import INDUSTRY_FIELD from '@salesforce/schema/Account.Industry';

export default class AccountVersionProbe extends LightningElement {
    @api recordId;

    @wire(getRecord, {
        recordId: '$recordId',
        fields: [NAME_FIELD],
        optionalFields: [INDUSTRY_FIELD]
    })
    account;

    get hasRecordId() {
        return Boolean(this.recordId);
    }

    get hasData() {
        return Boolean(this.account?.data);
    }

    get hasError() {
        return Boolean(this.account?.error);
    }

    get accountName() {
        return this.hasData
            ? getFieldValue(this.account.data, NAME_FIELD)
            : '';
    }

    get industry() {
        if (!this.hasData) {
            return '';
        }

        return (
            getFieldValue(this.account.data, INDUSTRY_FIELD) ||
            'Not provided or unavailable'
        );
    }
}
```

### Template: observable states without raw error payloads

```html
<!-- accountVersionProbe.html -->
<template>
    <lightning-card title="Account version probe">
        <div class="slds-p-around_medium">
            <template lwc:if={hasRecordId}>
                <template lwc:if={hasError}>
                    <p role="alert">
                        Account data could not be loaded.
                        Contact your administrator if this continues.
                    </p>
                </template>
                <template lwc:elseif={hasData}>
                    <dl>
                        <dt>Account</dt>
                        <dd data-testid="account-name">{accountName}</dd>
                        <dt>Industry</dt>
                        <dd data-testid="industry">{industry}</dd>
                    </dl>
                </template>
                <template lwc:else>
                    <p role="status">Loading account…</p>
                </template>
            </template>
            <template lwc:else>
                <p role="status">Open this component on an Account record.</p>
            </template>
        </div>
    </lightning-card>
</template>
```

### Metadata: the version boundary

```xml
<?xml version="1.0" encoding="UTF-8"?>
<LightningComponentBundle xmlns="http://soap.sforce.com/2006/04/metadata">
    <apiVersion>68.0</apiVersion>
    <isExposed>true</isExposed>
    <masterLabel>Account Version Probe</masterLabel>
    <targets>
        <target>lightning__RecordPage</target>
    </targets>
    <targetConfigs>
        <targetConfig targets="lightning__RecordPage">
            <objects>
                <object>Account</object>
            </objects>
        </targetConfig>
    </targetConfigs>
</LightningComponentBundle>
```

Deploy the bundle through your normal sandbox process, add it to an Account record page, and activate that page for your test audience.

For a controlled comparison, first deploy this same bundle with `apiVersion` set to `67.0`. Capture results, then change only that value to `68.0` and repeat.

The required Name field and optional Industry field create a useful permission test. The [`getRecord` documentation](https://developer.salesforce.com/docs/platform/lwc/guide/reference-wire-adapters-record.html) explains that inaccessible required fields produce an error, while inaccessible optional fields are omitted without failing the request.

### What this example proves—and what it does not

Use the component to check:

- Successful data rendering.
- An empty Industry value.
- Industry omitted for a restricted user.
- A record-access failure.
- Initial loading and subsequent data delivery.
- Repeated navigation between Account records.

The wire service provides reactive data and can provision values from its cache rather than making a network request every time. Do not write tests that assume every render causes a fetch. See [Understand the Wire Service](https://developer.salesforce.com/docs/platform/lwc/guide/data-wire-service-about.html).

This probe is a diagnostic aid, not certification of your application. It does not cover custom events, third-party scripts, editable forms, or console navigation. Add those cases to the actual components that use them.

## Require three layers of evidence

### 1. Static review and deployment diagnostics

Start with a version inventory. For each bundle, record:

- Current and target API version.
- Owner and business workflow.
- Parent and child dependencies.
- Relevant intermediate-release changes.
- Known warnings and accepted exceptions.
- Previous deployable artifact.

Salesforce’s [Upgrade a Component’s API Version](https://developer.salesforce.com/docs/platform/lwc/guide/create-version-upgrade.html) recommends resolving deployment and browser-console warnings, incrementing the version, and testing again. It also warns that a warning in one version can become an error in the next.

Make warning review a release gate, not background cleanup.

### 2. Local unit tests

Write tests for rendering, data transformations, events, and failure states. For the example above, mock successful data, omitted optional fields, and an error response.

Salesforce describes Jest tests as local, isolated component tests. They are not deployed to Salesforce, and mocked Apex calls do not execute Apex. See [Write Jest Tests for Lightning Web Components](https://developer.salesforce.com/docs/platform/lwc/guide/unit-testing-using-jest-create-tests.html).

Do not treat changing `apiVersion` and rerunning Jest as a faithful 67-versus-68 runtime comparison. Salesforce’s [component-level versioning explanation](https://developer.salesforce.com/blogs/2024/01/introducing-component-level-api-versioning-for-lwc) specifically distinguishes local testing from the platform’s versioned execution environment.

### 3. Browser tests in the target environment

My minimum browser checklist is:

- Initial load, empty state, denied access, and recovery.
- Keyboard navigation and visible focus.
- Parent-child property and event contracts.
- Repeated navigation and component recreation.
- Supported mobile or Experience Builder surfaces, where used.
- Representative data volume.
- Console warnings and failed requests.

Run permission-sensitive workflows as representative users, not only administrators. Keep security-setting changes and UI refactors out of the version-only deployment.

## Operate the rollout, not just the deployment

### Observability

Before deployment, define the evidence that would make you stop:

- New client-side exceptions.
- Broken critical workflows.
- Permission failures outside the established baseline.
- Material deterioration in page responsiveness.
- Repeated loading states without completion.

Set thresholds from your own baseline rather than borrowing arbitrary percentages.

Where you have telemetry, record a component identifier, deployment identifier, workflow, timing, and sanitized error category. Avoid logging full records, access tokens, or raw wire payloads. Sample and cap telemetry so the diagnostic mechanism does not become a workload of its own.

### Limits and cost

Lightning Data Service shares cached records across components and does not incur API usage calls, although general limits still apply. Salesforce documents those properties in [Lightning Data Service](https://developer.salesforce.com/docs/platform/lwc/guide/data-ui-api.html).

For this upgrade, budget primarily for engineering review, browser testing, sandbox capacity, and monitoring retention. Do not assume that changing the version number alone creates a measurable performance improvement.

Use narrow field requests where appropriate. Salesforce recommends requesting specific fields rather than layouts when possible for performance; see [`getRecord`](https://developer.salesforce.com/docs/platform/lwc/guide/reference-wire-adapters-record.html).

### Rollout and rollback

Promote a small, well-understood batch first. Keep unrelated business changes out of it.

Preserve the **complete previous bundle**, not just its version number. If a later change introduces syntax or APIs unavailable in the older version, a metadata-only reversal is not an adequate recovery plan.

A controlled audience also needs a real exposure mechanism. If you intend a canary release, explicitly design a separate candidate component and page assignment, or another tested routing mechanism. Do not merely label a shared-component deployment “canary” in the release ticket.

Finally, distinguish application recovery from platform recovery. Redeploying your previous artifact cannot freeze Lightning Data Service or base-component implementations; those remain outside the custom component’s version boundary, as documented in [Upgrade a Component’s API Version](https://developer.salesforce.com/docs/platform/lwc/guide/create-version-upgrade.html).

If the current-release baseline fails before you change `apiVersion`, stop attributing the issue to API 68. Investigate that baseline failure first.

## TL;DR

- **API 68.0 has no documented version-specific LWC changes.** Older components still need review of intervening versions, not a blind jump.
- **Versioning protects a defined component-framework boundary, not the whole platform.** Base components and Lightning Data Service remain shared dependencies.
- **Compare, then promote:** test unchanged metadata on Winter ’27, change one bundle at a time, and retain a tested recovery artifact.
